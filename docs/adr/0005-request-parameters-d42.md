# ADR 0005. d42-схемы параметров запроса: строковый вид поверх типизированной схемы

- Статус: принято
- Версия библиотеки: 0.6.0
- Контекст: до 0.6.0 d42 генерировался только для тел. У параметров была
  одна JSON Schema (`ParameterView.json_schema`), а у GET с одними
  query-параметрами d42-модуля запроса не было вовсе. Первая такая операция в
  Tandava E2E (`getFolderRoleIdmLink`: `folderId` int64 и `action` enum) получила
  самодельную схему, где оба параметра стёрты до `schema.str`. При переводе
  остальных доменов таких операций будут десятки: в спецификации Tandava 207
  целочисленных параметров, 9 enum и 11 массивов.

## Проблема

Значение HTTP-параметра — всегда строка: `?folderId=42&action=READ`. Тест
сравнивает перехваченный запрос именно в этом виде, поэтому типизированная
d42-схема значения (`schema.int`) здесь не подходит. `ContractMock` при выходе
уже проверяет тип и `enum` параметров по JSON Schema. Точных значений (чужой
`folderId`, валидный, но не тот `action`) он не проверяет, и эту проверку тест
пишет сам.

Нужна d42-схема «имя параметра → значение в виде на проводе», которая:

1. не уже контракта: всё, что проходит проверку запроса по контракту, проходит
   и её (для значений; ключи заголовков — см. решение 2);
2. даёт `fake()` значения, которые проходят проверку запроса по контракту;
3. поддерживает `%` и типизированным значением (`42`), и строкой (`"42"`).

## Решение 1. Строковый вид значения — отдельный тип d42 `serialized(...)`

`serialized(schema.int.min(1).max(100))` проверяет строку правилом разбора
перехваченного запроса (`geas.runtime.validation.decode_scalar`) и прогоняет
разобранное значение через вложенную схему. Границы, `enum`, `uniqueItems`
остаются в типизированной схеме и проверяются точно. `fake()` генерирует
значение вложенной схемы и записывает его строкой (`encode_scalar`: `True` →
`"true"`).

Правило разбора одно на всю библиотеку. Его используют проверка
перехваченного запроса, d42-схема параметров и закрепление `query_params` мока.
Поэтому значение, прошедшее одну из этих проверок, пройдёт и остальные. Ведущие
нули (`"007"`) проверка запроса принимает, и схема их принимает тоже.

`%` работает двумя способами:

- **строкой** — закрепляет точный вид на проводе и возвращает `schema.str(...)`;
- **значением** — закрепляет само значение: `serialized(schema.int) % 42` примет
  и `"42"`, и `"042"`. Так `% 1.0` для `number` не разойдётся с клиентом на JS,
  который отправит `"1"`. `True` для `integer` отклоняется: в Python `bool` —
  подкласс `int`, и без явной проверки флаг ушёл бы в запрос строкой `"true"`.

Строковый query-параметр не оборачивается: его значение и есть строка запроса, и
обычная `schema.str` с `enum`/`pattern`/границами точна. Путь внутрь
`serialized` прозрачен для overlay'ев: подмена `("folderId",)` схемой
`ValidIDSchema` меняет генератор типизированного значения.

### Ограничения транспорта: `location`

Строку в path, header и cookie транспорт ограничивает сам. Сегмент маршрута не
бывает пустым (шаблон сопоставляется с `[^/]+`) и не содержит `/`: aiohttp отдаёт
путь уже раскодированным, и `%2F` в нём становится разделителем. HTTP срезает пробелы по краям
значения заголовка, разбор cookie режет пары по `;` и тоже срезает пробелы.
Разобранный запрос таких строк не содержит, но `fake()` по голой `schema.str` их
выдаёт: в алфавите d42 есть пробел, длина начинается с нуля, генератор по
`pattern` выдаёт пунктуацию. Независимое ревью воспроизвело это: 3 из 3000 пустых
сегментов у массива строк в path, 93 из 3000 у `pattern: "^[a-z]*$"`, 128 из 2000
значений cookie с `;`.

Поэтому строка в этих местах оборачивается в
`serialized(schema.str..., location="path" | "header" | "cookie")`. Правило
места проверяется и при валидации, и при генерации: `fake()` перебирает
варианты, пока текст не пройдёт свою же проверку. Уже контракта проверка не
становится, потому что после разбора запроса такой текст не встречается.
Числа и флаги правило выполняют всегда, их запись непустая и без пробелов.
Регулярку вида `(?!^$)` здесь не используют: d42 не совмещает `regex()` с
`len()`, а у строки с `pattern` пришлось бы переписывать чужое выражение.

### Отвергнутые варианты

- **`schema.str.regex(r"^-?\d+$")`.** Проверено на d42 2.4.0: `fake()` выдаёт
  строки до 33 цифр, и половина из них отрицательные. Для int64 и `minimum: 1`
  такое значение не пройдёт контракт, что нарушает требование 2. Границы в
  такой регулярке не выражаются.
- **Точная регулярка диапазона** (range → regex). Для int64 получается
  альтернатива на 300+ символов, нечитаемая в generated-файле и в тексте
  ошибки. Она отвергает `"007"`, которое проверка запроса принимает, то есть
  сужает контракт. Для `number` с границами регулярки нет вовсе.
- **Типизированная схема и приведение в хелпере потребителя.** Так у Tandava
  появился `build_expected_params_schema`: приведение живёт в каждом проекте
  отдельно и расходится с правилом разбора Geas (`str(True) == "True"`).

## Решение 2. Схема на место запроса, отдельный модуль, отказ по месту

Для каждого места с параметрами (path, query, header, cookie) генерируется одна
d42-схема-словарь. Все схемы места лежат в модуле
`_d42/<slug>_request_parameters.py`, отдельном от модуля тела. Доступ к схеме —
`operation.d42_schema(Direction.REQUEST, part="query")`.

- Необязательный параметр объявлен ключом `optional(...)`.
- Ключи схемы заголовков — имена из контракта. Имена заголовков в HTTP
  регистронезависимы, а у d42-словаря ключи чувствительны к регистру, поэтому
  перед сравнением имена перехваченного запроса приводятся к именам контракта
  (это делает потребитель). Делать словарь регистронезависимым (отдельный тип
  d42) пока не стали: таких операций в известных проектах одна, а заголовки
  там по-прежнему проверяет `ContractMock`.
- Словари query, header и cookie открыты (`...: ...`): контракт не запрещает
  необъявленные параметры, а заголовки `Host`, `User-Agent` есть в любом
  запросе. Словарь path закрыт: его ключи задаёт шаблон маршрута.
- Пустая строка nullable-строки разбирается в `null` и допустима.

Место отказывает отдельно от остальных. Сериализация, пропущенная waiver'ом
`allow_unsupported_serialization` (`deepObject`, `label`, `matrix`), не имеет
строкового вида, который библиотека умеет разбирать. Заголовки, различающиеся
только регистром, неразличимы в запросе. В обоих случаях схема этого места не
строится, причина печатается в `geas update` и попадает в документ контракта
(`d42.parameters_reasons`). Её же называет `d42_schema(part=...)`. Схемы
соседних мест и d42 тела остаются.

Всё про d42 параметров лежит в разделе `d42` документа контракта
(`parameters_module`, `parameters`, `parameters_reasons`). Раздел
несемантический, поэтому обновление Geas не даёт смысловых изменений в
`geas diff`.

## Решение 3. Массивы — по их сериализации

- **Повторы ключа** (query, `form`, `explode: true`, по умолчанию для query)
  описываются списком строковых видов элементов: `{"status": ["draft", "review"]}`.
  Ноль повторов означает отсутствие параметра, поэтому элементов минимум один.
  У `uniqueItems` с `enum` или `boolean` верхняя граница равна числу значений.
  Сужением это не будет: различных элементов больше не бывает, а генератор d42
  не упирается в нехватку уникальных значений.
- **Одна строка через разделитель** (`explode: false`, `spaceDelimited`,
  `pipeDelimited`, массивы в path и header) описывается как
  `serialized(schema.list(...), delimiter=",")`. Пустая строка разбирается в
  один пустой элемент, как и при проверке запроса. Поэтому пустой массив в
  таком виде не выражается, и элементов минимум один. Литерал `enum`, который
  содержит разделитель, делает разбор неоднозначным, и такое место отказывает.
  Строка-элемент может содержать разделитель (в алфавите d42 есть пробел), поэтому
  `fake()` перебирает варианты, пока строка не пройдёт свою же проверку. Если
  за 100 попыток подходящий вариант не найден, он падает с подсказкой задать
  значение через `%`.

## Попутно: `ContractMock(query_params=...)`

Раньше значения уходили в матчер JJ через `str()`, без проверки по контракту:
`True` становилось `"True"`, значение вне `enum` закреплялось молча, и мок
падал на выходе с «перехвачено 0 запросов». Теперь при создании мока:

- неописанный параметр вызывает `ContractMockError`, как у `path_params`;
- то же правило действует для `path_params` и описанных контрактом `headers`;
  заголовки вне контракта (`Authorization`) закрепляются строкой без проверки;
- `None` записывается пустой строкой — так `null` выглядит в запросе. Если у
  параметра пустая строка в `null` не разбирается (число, флаг, не-nullable
  строка), это `ContractMockError` сразу при создании мока;
- значение сначала становится строкой матчера (`encode_scalar` для `bool`,
  `int`, `float` и `str`, `str()` для `UUID`, `date` и прочих), и уже эта строка
  разбирается по контракту тем же правилом, что перехваченный запрос. Поэтому
  `{"page": 1}` для строкового параметра и `UUID` для `format: uuid` работают
  как раньше, а значение, с которым не совпадёт ни один запрос, отклоняется
  сразу;
- у массива повторами ключа строка закрепляет один повтор и проверяется по схеме
  элемента: матчер JJ совпадает, если совпал хотя бы один повтор. Список целиком
  не закрепляется, потому что матчер сравнивает одно значение. Массив одной
  строкой можно передать списком, он склеится через разделитель стиля.

## Последствия

- Alias схемы параметров в проекте-потребителе становится однострочным, как у
  тела.
- `format` (`date-time`, `uuid`) в d42-схемах параметров, как и в схемах тел, не
  проверяется и не генерируется. `fake()` для такого параметра даёт строку,
  которую отклонит JSON Schema с проверкой `format`. Такие поля задаются через `%`
  или overlay.
- Для d42-схемы открытого словаря лишний параметр допустим. Отсутствие
  параметра проверяется отдельным `not in`, как и у тел.
- Заголовки ответа d42-схем не получают: в тестах их задают, а не проверяют.
- `uniqueItems` у массива повторами ключа d42 проверяет по строкам на проводе, а
  контракт — по разобранным значениям. `["1", "01"]` d42-схема пропустит, а
  проверка запроса в `ContractMock` отклонит. `fake()` пишет значения канонически
  (`str(int)`, `repr(float)`), поэтому его массивы уникальны и по значению. Ради этого
  у `number` в параметрах нет целой ветки `json_int`, как у тел с 0.5.1: строка всё
  равно разбирается во `float`, а с целой веткой `fake()` выдавал бы `"2"` и `"2.0"`.

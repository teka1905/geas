# ADR 0001. Архитектура openapi-contract-fixtures

- Статус: принято
- Версия библиотеки: 0.1.0
- Контекст: библиотека выделяется из внутреннего прототипа, который смешивал нормализацию
  OpenAPI, генерацию d42-схем и runtime-моки в одном модуле.

## Проблема

Тесты используют захардкоженные фикстуры и моки. Когда бэкенд меняет контракт,
тесты продолжают проходить на устаревших данных — *contract drift*. Нужен
воспроизводимый пайплайн:

```
checked-in OpenAPI
  → нормализованный контракт (IR)
  → generated JSON Schema и d42
  → generator overlays
  → generated operation handles
  → operation-aware JJ mocks
  → проверка drift в CI
```

## Решение 1. Четыре уровня, ядро не зависит от d42 и JJ

```
openapi_contracts/            ядро: manifest, IR, нормализация, JSON Schema, артефакты, CLI
openapi_contracts/dialects/   адаптеры диалектов: swagger2, openapi30 (в будущем openapi31)
openapi_contracts/integrations/d42/   опционально: IR → d42 2.x, рендер, overlays
openapi_contracts/integrations/jj/    опционально: OperationHandle.mock() → JJ
```

Ядро импортирует только `jsonschema` и `PyYAML`. Ни один модуль ядра не импортирует
`d42` или `jj` — ни на уровне модуля, ни внутри функций, кроме двух точек входа
`OperationHandle.d42` и `OperationHandle.mock()`, которые делают отложенный импорт и
при отсутствии extra бросают `MissingExtraError` с точной командой установки.

Это проверяется тестами, которые импортируют ядро и generated-реестр в подпроцессе,
где `d42` и `jj` заблокированы в `sys.modules`.

**Почему.** Потребители — тестовые проекты. Часть из них хочет только JSON Schema и
CI-проверку drift, без d42. Часть — только фикстуры, без JJ. Жёсткая зависимость
превратила бы библиотеку в транзитивный источник конфликтов версий `aiohttp`.

### Границы

| Уровень | Отвечает за | Не знает про |
| --- | --- | --- |
| core | manifest, IR, `$ref`, нормализация, provenance, fingerprints, semantic diff, waivers, JSON Schema, артефакты, CLI | d42, JJ, HTTP |
| dialects | различия Swagger 2.0 / OpenAPI 3.0.x → общий IR | d42, JJ, артефакты, CLI |
| integrations/d42 | IR → d42 2.x, рендер `.py`, fixtures, overlays | JJ, диалекты, файловые артефакты |
| integrations/jj | matcher/response, регистрация мока, history, request validation | диалекты, d42 (кроме опциональной проверки через ядро) |

Диалектные различия обязаны исчезать на границе `dialects/` — ниже по стеку нет ни
одного `if spec_version == ...`.

## Решение 2. JSON Schema dialect — Draft 2020-12

Нормализованный контракт публикуется как **JSON Schema Draft 2020-12**
(`$schema: https://json-schema.org/draft/2020-12/schema`).

**Почему именно 2020-12:**

- это дефолтный и наиболее полно поддержанный диалект в `jsonschema>=4`;
- `$defs` + `$ref` дают точное представление именованных схем;
- `if`/`then` позволяет выразить OpenAPI `discriminator` как **настоящее ограничение
  валидации**, а не как подсказку генератору;
- `prefixItems`, `dependentRequired`, числовой `exclusiveMinimum/Maximum` убирают
  расхождения OpenAPI 3.0 с обычной JSON Schema.

**OpenAPI Schema Object не передаётся в `jsonschema` напрямую.** Swagger 2.0 и
OpenAPI 3.0 — это *подмножество Draft 4 с расширениями*, а не JSON Schema. Мы
транслируем явно:

| OpenAPI / Swagger | JSON Schema 2020-12 |
| --- | --- |
| `nullable: true` (3.0), `x-nullable: true` (2.0) | `type: [T, "null"]`, либо `anyOf: [S, {"type": "null"}]` для композиции |
| `exclusiveMinimum: true` + `minimum: N` (3.0/2.0) | `exclusiveMinimum: N` |
| `readOnly` / `writeOnly` | удаляются из противоположного направления ещё в IR |
| `discriminator` | `oneOf` + `allOf` из `if/then` по `propertyName` + `required` |
| `example`, `description`, `xml`, `externalDocs`, `deprecated` | отбрасываются из семантической схемы |
| `format` | сохраняется, но только из allowlist; неизвестный `format` — ошибка |

Разрешение `$ref` при валидации идёт **только** через локальный in-memory
`referencing.Registry`. Сетевого разрешения нет: `retrieve` — функция, которая
всегда бросает исключение.

## Решение 3. Fail-closed нормализация

Ни одна неподдержанная конструкция не превращается в `schema.any`, пустой объект или
предупреждение. Любая из них — исключение `UnsupportedConstructError` c четырьмя
координатами: `source`, `operation key`, `direction`, `JSON Pointer`.

Единственный способ ослабить проверку — явный waiver в `waivers.yaml`, ограниченный
конкретной операцией, направлением, указателем и правилом.

Рекурсивные схемы **отклоняются**, а не поддерживаются частично: d42 не умеет
выражать рекурсию, поэтому «поддерживается всеми представлениями» недостижимо.
Эскейп-хетч — waiver `replace_schema` с `expected_source`.

Внешние HTTP `$ref` запрещены всегда. Локальные межфайловые `$ref` разрешены только
внутри явно заданного `root` источника, с защитой от `..`, symlink-escape,
выхода за root и TOCTOU (файл читается один раз, дальше — из in-memory реестра).

## Решение 4. Публичный mock API — async context manager, без декоратора

```python
async with operations.ws2.add_ticket.mock(
    response=response_body,
    path_params={"queueId": queue_id},
    wait_for_requests=1,
) as mock:
    await page.submit()
```

**Почему async context manager, а не декоратор.**

Контракт нужно проверить в двух разных точках жизненного цикла:

1. **до** регистрации мока — response body по generated d42 и независимо по JSON
   Schema; неверный мок не должен доехать до приложения;
2. **после** выхода из блока — каждый перехваченный request (метод, маршрут,
   path/query/header/cookie параметры, тело, content type, сериализация).

Вторая проверка принципиально *post-hoc*: она возможна только когда история запросов
уже собрана и мок снят. Context manager — единственная конструкция, у которой есть
обе точки, детерминированный порядок и гарантированный cleanup при исключении.
Дополнительно он естественно отдаёт пользователю `history` после выхода, что нужно
для cardinality-ассертов на стороне теста.

**Почему декоратор отложен.** Декоратор над сценарием даёт ту же семантику, но:

- он вынужден догадываться, куда отдать `ContractMock` (по имени аргумента или
  позиционно) — это неявная магия;
- он создаёт *второй* execution path для валидации, который придётся держать в
  синхроне с основным;
- реального boilerplate, который он бы устранил, пока не подтверждено: существующие
  потребительские `mocked_*`-обёртки остаются тонкими функциями поверх
  `OperationHandle.mock()` и мигрируют без изменения call sites.

Поэтому в v0.1 декоратора нет. Если миграция нескольких проектов покажет
повторяющийся boilerplate, будущий декоратор обязан: принимать публичный `MockCase`,
делегировать тому же `OperationHandle.mock()`, возвращать тот же `ContractMock`, не
анализировать готовый `jj.Mocked` и не менять семантику валидации.

Persistent-моки в v0.1 не поддерживаются: `start()` без обязательного
`close_and_validate()` позволил бы молча пропустить валидацию.

## Решение 5. Generated namespace строится из стабильного ключа manifest

`operations.ws2.add_ticket` порождается из ключа `ws2.addTicket`, а не из
изменяемого `operationId`. Если бэкенд переименовал `operationId`, падает
manifest binding — но публичное Python-имя не переименовывается само.

Namespace — статический Python-код с аннотациями (никакого `__getattr__`), чтобы
работали IDE-автодополнение и mypy. Строковый доступ `operations.by_key("ws2.addTicket")`
оставлен как escape hatch для инструментов, но не рекомендуется в тестах.

Все коллизии (Python keywords, невалидные идентификаторы, совпадение после
нормализации, конфликт leaf и namespace, зарезервированные атрибуты, коллизии между
источниками) — ошибка генерации. Числовые суффиксы молча не добавляются; разрешение —
только явный `python_path` в manifest.

Изменение generated Python path считается breaking semantic diff.

## Решение 6. OpenAPI 3.0 сейчас, 3.1 — отдельным адаптером потом

OpenAPI 3.1 **не** считается совместимым с 3.0: в 3.1 `nullable` удалён,
`exclusiveMinimum` числовой, `type` может быть массивом, а Schema Object — полноценная
JSON Schema 2020-12. Молча обработать 3.1 как 3.0 значит тихо потерять `null` в
типах и неверно разобрать границы.

Поэтому `dialects/` — реестр адаптеров по версии документа. В v0.1 зарегистрированы
`swagger2` и `openapi30`; документ с `openapi: 3.1.x` даёт
`UnsupportedSpecVersionError` с точным текстом и указанием, что адаптер 3.1 появится
отдельно. Добавление 3.1 — это новый модуль `dialects/openapi31.py` и запись в
реестре, без изменений в ядре, генераторе, runtime и CLI.

## Решение 7. d42 2.x, без совместимости с 1.x

Целевая версия — `d42>=2,<3`. В 2.x доступен публичный интроспекционный API,
которого достаточно для overlays без обращения к приватным классам:

- `schema.props` → `DictProps.keys` вида `{key: (schema, is_optional)}`;
- `props.update(...)` и `schema.__class__(props)` для построения новой схемы;
- `d42.declaration.types` экспортирует все классы схем и `optional`;
- `d42.utils.make_required` — публичный;
- `d42.declaration.union` / оператор `|` → `AnySchema` с `props.types`.

`% ` (substitution), `fake()` и `make_required()` продолжают работать с overlay-схемами,
потому что overlay возвращает обычную d42-схему того же класса.

`fake()` в d42 2.x **никогда не генерирует optional-ключи** — это и даёт свойство
«добавление optional-поля не меняет стабильную фикстуру». Для union `fake()`
выбирает вариант случайно, поэтому фикстуры библиотеки генерируются не через
`fake()` напрямую, а через детерминированную проекцию: union сворачивается в свой
первый вариант в стабильном порядке контракта, а генератор получает
фиксированный seed. Добавление варианта в конец union не меняет фикстуру.

`oneOf` в d42 проецируется в `schema.any(...)`, что шире исходной семантики
(эксклюзивность теряется). Поэтому **валидация response и request всегда идёт двумя
независимыми путями**: d42 и JSON Schema. Точная семантика `oneOf` и `discriminator`
сохраняется в JSON Schema и проверяется всегда, а не «в лучшем случае». В IR и
generated JSON Schema `oneOf` никогда не заменяется на `anyOf`.

## Решение 8. Детерминированные generated-артефакты и transactional CLI

`update` пишет во временную директорию и переносит результат атомарно; удаляет только
файлы, записанные генератором как owned; проверяет containment и symlink-escape.
`check` генерирует в temp и сравнивает, ничего не меняя в рабочем дереве.
`add` полностью нормализует и рендерит операцию во временную директорию до того, как
тронуть manifest: при неподдержанной конструкции manifest остаётся byte-identical.

Детерминизм: стабильная сортировка, UTF-8, `\n`, без timestamp, без абсолютных путей,
без UUID. Повторный `update` без изменения входов даёт byte-identical результат.

`description`, `example`, документационные расширения и порядок ключей не влияют на
semantic fingerprint.

## Последствия

- Ядро можно тестировать без сети, без d42 и без JJ.
- Добавление 3.1 не трогает ядро.
- Потребитель, которому нужен только drift-check в CI, ставит `openapi-contract-fixtures`
  без extras.
- Плата: `oneOf` в d42-проекции шире контракта, поэтому JSON Schema-валидация
  обязательна и не может быть отключена.
- Плата: рекурсивные схемы не поддерживаются в v0.1.

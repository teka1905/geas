# ADR 0003. d42 для рекурсивных контрактов: отсечка цикла

- Статус: принято
- Версия библиотеки: 0.5.0
- Контекст: у потребителя (Tandava) рекурсивны все 11 операций сценариев
  чат-ботов из 28 в домене и дерево папок `FolderTreeDto`. Цикл сидит глубоко
  внутри DTO, но до 0.5.0 он выключал d42 для операции целиком — и для
  нерекурсивной части ответа, и для тела запроса, где рекурсии нет вовсе.
  Потребители закрывали это ручными «конвертами» со сверкой по JSON Schema на
  импорте.

## Проблема

d42-схема строится «по значению»: `schema.dict({...})` содержит сами дочерние
схемы, а не ссылки на них. Рекурсивный `$ref` так не выразить — развёртка не
кончится. До 0.5.0 это решалось грубо:

- `contracts.py` ставил флаг `recursive` по запросу и ответу вместе, и
  `d42_enabled` становился `False` для обоих направлений;
- рендер артефактов при любой ошибке d42 в одном направлении отключал и второе.

Ручной конверт возвращает `%` и `fake()`, но дублирует контракт руками и держит
его актуальность на самописной сверке.

## Решение 1. Отсекать цикл, а не отключать d42

Граф определений направления обходится в глубину от корней модуля — тел
вариантов в порядке контракта; дальше свойства по имени, тип дополнительных
значений, элементы массивов, варианты объединений по порядку. Ссылка `A → B`, где
`B` уже лежит на текущем пути обхода, замыкает цикл: в плане `A` все ссылки на `B`
заменяются листом. Остальные ссылки не трогаются, поэтому определение
типизировано вплоть до места, где цикл замкнулся.

**Почему от корней, а не от всех определений по алфавиту.** Обход по алфавиту
не зависит от операции, но режет цикл в случайном с точки зрения смысла месте.
Для `EdgePredicateV2Dto → And/Or → EdgePredicateV2Dto` он начал бы с `And` и
отсёк бы `EdgePredicateV2Dto → And`: `And` и `Or` оказались бы типизированы
по-разному. Обход от корня входит в цикл там же, где его видит пользователь
(через `EdgePredicateV2Dto`), и отсекает `And.args` и `Or.args` одинаково.
Цена — одно и то же определение в модулях разных операций может быть
типизировано на разную глубину. Внутри модуля отсечка одна: определения
рендерятся один раз.

**Почему не по компонентам сильной связности.** Резать все рёбра внутри
компоненты проще, но тогда `NodeCreateDto.executorTypeInfo` превратился бы в лист
сразу при входе в цикл `SectionDto → … → NodeCreateDto`, и типизированной
осталась бы только верхушка. Отсечка по обратным рёбрам обхода минимальна: лист
появляется ровно там, где без него обход не закончится.

## Решение 2. Лист проверяет по JSON Schema, остальное делегирует d42

Лист — кастомный тип d42 `RecursiveRefSchema`:

| Операция | Поведение |
| --- | --- |
| валидация | JSON Schema определения со всеми достижимыми `$defs`, без `format` |
| `%` | делегируется типизированной схеме того же определения |
| `fake()` | минимальный экземпляр, сверенный с JSON Schema |
| `make_required()` | не затрагивается (он поверхностный и у d42) |
| overlay | путь до листа или сквозь него — `ContractOverlayError` |

**Валидация по JSON Schema, а не «что угодно».** `schema.dict` на месте цикла
пропускал бы любое значение, и d42-путь перестал бы что-либо гарантировать в
рекурсивной части. JSON Schema определения держит всё, что держит контракт:
обязательность, `enum`, `pattern`, `oneOf`, `discriminator` и саму рекурсию.

**Без `format`.** d42 не генерирует и не проверяет `format` нигде (шапка
`geas.integrations.d42.converter`, «точность перевода»): это работа JSON-Schema-пути `validate_*` и моков,
который видит рекурсию целиком. Проверяй лист `format`, `build_fixture` отвергал
бы собственную фикстуру: сгенерированная строка не является ни uuid, ни датой.

**`%` через типизированную схему.** Подстановка d42 частичная: у словаря можно
закрепить часть ключей. Если бы лист принимал только значение целиком, дерево
пришлось бы описывать полностью на каждом уровне. Делегирование в схему
определения даёт ту же частичность на любой глубине — ровно то, что ручные
генераторы деревьев делали в обход контракта.

**`fake()` — минимальный экземпляр.** Обычная генерация d42 для списка выбирает
длину 0..16, и каждый элемент-лист снова генерировал бы список: дерево растёт
экспоненциально и может не закончиться. Поэтому лист генерирует минимальный
экземпляр: обязательные поля, массивы минимальной длины, в объединении — первый
вариант, из которого есть выход из цикла. Выход ищется неподвижной точкой по
рангам: определение получает ранг `r`, если строится из определений ранга меньше
`r`, и генерация спускается только к листьям строго меньшего ранга. Это
гарантирует завершение и детерминизм выбора. Определение без конечного значения
(цикл только через обязательные поля) даёт `RecursiveSchemaError`, а минимальный
экземпляр, не прошедший JSON Schema (неоднозначный `oneOf`), —
`ValidationFailedError`. Обе ошибки советуют задать значение через `%`.

**Overlay не пересекает лист.** Инвариант overlay'ев — подменяется только
генератор листа, структура остаётся сгенерированной (шапка
`geas.integrations.d42.overlays`). За листом —
структура, которую d42 не развернул, и подмена её генератора была бы подменой
контракта. `%` решает ту же задачу без нарушения инварианта.

## Решение 3. Позднее связывание и JSON Schema внутри модуля

Лист нужен раньше, чем схема его определения. Модуль создаёт
`_RECURSION = RecursionContract({...})` с JSON Schema отсечённых определений и
всего, что из них достижимо, строит схемы через `_RECURSION.ref("Имя")` и после
определений вызывает `_RECURSION.bind({...})`.

- Связь хранится в контракте, а не в `props` листа: равенство d42 сравнивает
  `props`, и цель внутри них сделала бы `==` и `repr` бесконечными. Два листа
  равны, если совпадают имя и JSON Schema.
- JSON Schema встраивается в модуль, а не читается из `contracts/<slug>.json`.
  Модуль остаётся самодостаточным, не зависит от раскладки артефактов и не
  читает файлы при импорте, а `exec` модуля по-прежнему даёт схемы, равные
  `to_d42` (гарантия рендера). Цена — дублирование части контракта в артефакте.

## Решение 4. Направления независимы

Рекурсия больше не выключает d42. Невыразимая конструкция (`allOf`,
`multipleOf`, ...) выключает d42 только того направления, где она встретилась:
в документе контракта — `d42.<direction>_module: null` и
`d42.<direction>_reason`, сводная причина остаётся в `d42.reason`. Флаг
`d42.recursive` стал справочным.

## Последствия

- `geas update` печатает место каждой отсечки: `операция (направление): цикл
  отсечён на ссылке A -> B`.
- Потребитель заменяет ручной конверт рекурсивного DTO alias'ом на generated-схему,
  а ручной генератор дерева — `%`.
- d42 для операции по-прежнему может не сгенерироваться из-за других
  конструкций. У Tandava операции сценариев упираются ещё и в `allOf`
  (базовые `properties` + `oneOf` + `discriminator`), и отсечка цикла сама по себе
  их не разблокирует.
- Нижняя граница extra `[d42]` поднята до `d42>=2.3`: интеграция опирается на
  `optional.absent`. На более старой d42 импорт интеграции и `geas update`
  называют установленную версию, а не просят установить extra.

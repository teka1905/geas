# ADR 0007. Текстовые тела: `text/*` как строка и учёт тел без контракта

- Статус: принято
- Версия библиотеки: следующая после 0.6.0
- Задача: QAAUTOSAM-692
- Контекст: до этого изменения контракт строился только для JSON. Тело другого media type
  помечалось неподдержанным и выпадало из контракта операции. При переводе моков Samsara
  E2E на Geas (QAAUTOSAM-532) это дало три эффекта: мок ответа `text/plain` не создавался
  (`у операции нет варианта ответа *:*; доступны []`), тело запроса `text/plain` не
  проверялось вовсе, а диагностика говорила «нет тела», хотя спецификация его объявляет.

## Решение 1. Контракт строится для JSON и конкретных `text/*`

Тело `text/*` — строка целиком. Контракт для него — схема строки, а не отдельный вид
контракта: IR, JSON Schema, d42 и описание работают без изменений. Поэтому
`minLength`, `maxLength`, `pattern`, `enum`, `$ref` на именованную строку и
`allOf`/`oneOf`/`anyOf` из строк переносятся как у любой строки. Схема без ограничений,
принятая waiver'ом `allow_any`, под `text/*` означает «любая строка»: `validate_*` и мок
требуют `str`.

Поддержан весь `text/*`, а не только `text/plain`: `text/html`, `text/csv` и другие тоже
строки. Исключения:

- `text/*` как сам media type не называет формат тела, и мок не смог бы подписать ответ;
- `text/json` (умолчание Swashbuckle) — это JSON и получает JSON-контракт;
- `text/xml` и `…+xml` — XML (RFC 7303), `text/yaml` и `…+yaml` — YAML: структурированные
  форматы, для которых контракта нет, как и для `application/xml`;
- `text/event-stream` — поток событий (SSE), а не одно тело; springdoc описывает его
  массивом событий, и строкой проверять его нельзя.

Альтернатива: только `text/plain`. Отвергнута: `text/html` у серверных фреймворков
(фрагменты, превью) встречается так же часто, а граница «поддержан один тип» выглядела
бы произвольной.

## Решение 2. Схема не строка — ошибка у закреплённого варианта, `unchecked` у остальных

Объект, массив, число и `nullable`-строка под `text/*` текстом не проверить. Тихий
пропуск, как раньше, возвращал исходную проблему: вариант пропадал, а мок не
создавался. Что делать вместо него, зависит от того, просил ли пользователь этот
вариант явно:

- **закреплён в manifest** (`request.content_type`, `responses` — так записи делает
  `geas add --response 200:text/plain`): ошибка генерации `UnsupportedConstructError` с
  операцией, направлением, content type, JSON Pointer и причиной;
- **не закреплён**: вариант записывается в `unchecked` с причиной, `geas update`
  печатает её, остальные варианты строятся как обычно.

То же для схемы, которая не разбирается (нужен waiver, неизвестный `format`): у
закреплённого варианта — исходная ошибка нормализатора, у незакреплённого — `unchecked`
с её текстом (в нём есть и заготовка waiver'а). Если сырая схема заведомо не строка
(`type: object`, `properties`, `items`), причина — «схема описывает object» без
заготовки: waiver бы не помог. Так же обрабатывается устаревший waiver: waiver на
`/body` без `content_type`, выписанный для JSON-варианта, у текстового соседа не
совпадает с исходной схемой. Раньше текстовый вариант не нормализовался, и такой
waiver генерацию не ломал.

Почему не ошибка всегда. Такие варианты в реальных спецификациях почти всегда порождает
генератор, а не автор, и спецификация при этом валидна:

- Swagger 2.0 не умеет задавать media type статусу: `produces: [text/plain]` (или
  `[application/json, text/plain]`) размножает схему каждого ответа, в том числе `400`
  с объектом ошибки из `@ControllerAdvice`. Диалект помечает варианты из общего списка
  (`shared_media_type`: `produces` всегда, `consumes` — если он унаследован от корня);
- Swashbuckle (ASP.NET Core) объявляет каждый ответ в `text/plain`, `application/json`
  и `text/json` с одним `$ref`;
- springdoc для `text/csv` со списком DTO пишет схему массива.

На `main` такие спецификации генерировались, а ошибка уронила бы весь источник при
`selection: all`, где исключить один вариант нельзя. Причина в `unchecked` называет
вероятный источник: JSON-близнец с той же сырой схемой, общий список Swagger 2.0 или
«поправьте схему».

Это отступление от буквы требования «схема не string при text/* — явная ошибка
генерации»: ошибка остаётся для варианта, который пользователь выбрал явно, а
незакреплённый вариант не пропадает молча — он виден в `unchecked`, в `geas update` и в
ошибках выбора варианта.

Схема текстового варианта сначала пробуется отдельным нормализатором. Отвергнутый
вариант не оставляет определений (иначе его `$ref` отключал бы d42 у соседних
вариантов и добавлял лишние d42-схемы) и отметок waiver'ов (иначе устаревший waiver не
был бы назван). Принятый вариант нормализуется основным нормализатором.

Альтернативы:

- всегда ошибка — отвергнута по причине выше;
- ошибка только в OpenAPI 3.0 без JSON-близнеца — отвергнута: springdoc для `text/csv`
  и `text/yaml` даёт такие варианты и в OpenAPI 3.0;
- политика в manifest — отложена: закрепление варианта уже даёт строгий режим там, где
  он нужен.

## Решение 3. Тело запроса декодируется по `charset`, ответ отдаётся строкой

JJ декодирует тело запроса только у `text/plain` и всегда как UTF-8, а `charset` в
заголовке — обычное дело (`windows-1251`). Поэтому проверка берёт исходные байты и
декодирует их по `charset` из `Content-Type`; нет `charset` — UTF-8 (RFC 7231 убрал
ISO-8859-1 по умолчанию). JSON-разбор для `text/*` не выполняется: `"x"` в кавычках — это
три символа текста.

Ответ отдаётся как `jj.Response(text=...)`: строка уходит как есть, а `charset=utf-8`
дописывает JJ (aiohttp), если в `Content-Type` его нет. Свой `charset` задаётся в
`response_headers`; неизвестный `charset` или строка, которая в нём не кодируется, —
`ContractMockError` при создании мока, а не исключение из JJ на входе в `async with`.

## Решение 4. `Content-Type` запроса сопоставляется по media range

Спецификация может объявить диапазон (`*/*`, `image/*`), а клиент всегда шлёт конкретный
тип. Перехваченный запрос сопоставляется с объявленными телами по специфичности: точный
тип, затем `type/*`, затем `*/*`. Тело `*/*` разбирается по фактическому типу запроса:
JSON — как JSON, текст — как текст, бинарное тело не проверяется.

## Решение 5. Непроверяемое тело — структурная запись

`unchecked` в документе контракта (направление, статус, content type, причина,
`required` у запроса) рядом со строками в `unsupported`. Строки остались в прежнем
формате: по ним CLI и прежний код печатают причины, а смена формулировки дала бы ложное
изменение в `geas diff` у каждой такой операции. Структура нужна ошибкам выбора
варианта: они находят объявленный вариант и называют причину.

`unchecked` пишется только у операций с непроверяемыми телами: документы остальных не
меняются. Непроверяемые варианты записываются и тогда, когда в manifest закреплены
другие: закрепление выбирает среди проверяемых, а запрос с объявленным непроверяемым
`Content-Type` и мок со статусом такого варианта должны о нём знать. Непроверяемый
ответ закреплённой операции записывается, если его статус закреплён или у статуса нет
проверяемых вариантов: незакреплённый `404` с JSON- и XML-вариантом мок отдаёт через
`default`, как раньше, и посторонний XML-сосед этого не меняет.

`unchecked` семантический: изменение `required` у непроверяемого тела меняет поведение
проверки запроса. Исключение — появление ключа целиком в документе, где его не было
(миграция формата).

Запрос с объявленным непроверяемым `Content-Type` проходит без проверки тела; запрос с
типом, который не покрыт ни одним объявленным телом, отклоняется. Для операций, у
которых объявлены только непроверяемые тела, это ужесточение: раньше у них перехваченный
запрос не проверялся вовсе.

Мок со статусом, который объявлен хотя бы непроверяемым вариантом, не подменяется
вариантом `default`: иначе `mock(status=200)` при `200: application/octet-stream` молча
отдал бы схему `default`. Среди вариантов `default` выбор идёт по `content_type`.

## Решение 6. Варианты с одной схемой — один вариант

Распознавание `text/json`, `*/*` (в OpenAPI 3.0) и строкового `text/plain` добавило
варианты рядом с JSON, и `response(status=200)` без `content_type` стал бы падать с
неоднозначностью там, где раньше вариант был один. Если у всех подходящих вариантов
одного статуса (или у всех тел запроса) одна и та же схема, это один вариант в разных
написаниях: тело проверяется одинаково, и выбор главного (`application/json`, затем
другие конкретные JSON, затем `*/*` и `text/json`) — не «молча первый». Объединяются
только JSON-варианты: `text/plain` и `text/html` или JSON-строка и текст с одной схемой
уходят на провод по-разному, и для них `content_type` обязателен. Варианты с разными
схемами так не выбираются: `application/json` с объектом и `text/plain` со строкой
требуют `content_type`, и это описано в CHANGELOG как изменение совместимости.

`geas add` по той же причине закрепляет основной JSON-тип, если он один: `text/plain`,
`text/json` и `*/*` рядом с ним генераторы пишут по умолчанию.

## Решение 7. `*/*` — JSON в обоих диалектах

springdoc, как и JAX-RS, пишет `*/*` для JSON, поэтому правило Swagger 2.0 перенесено в
OpenAPI 3.0. Мок не подставляет `*/*` в `Content-Type`: тело JSON, и JJ подписывает его
`application/json`. Если в `response_headers` задан `text/*`, ответ уходит строкой.

Схемы `*/*` в OpenAPI 3.0 (и `text/json` в обоих диалектах) раньше не нормализовались
вовсе. Чтобы обновление не уронило источник, ошибка их схемы обрабатывается как у
текстового варианта: незакреплённый — `unchecked` с причиной, закреплённый — ошибка
генерации (диалект помечает такие варианты флагом `lenient`). `*/*` в Swagger 2.0 был
JSON и раньше и проверяется строго, как прежде.

Исключение — `*/*` со схемой `type: string, format: binary`: так springdoc описывает
выгрузку файла. Это байты, а не JSON-строка, и мок отдал бы их в кавычках с
`Content-Type: application/json`, поэтому вариант объявлен, но не проверяется — в обоих
диалектах.

## Решение 8. Имена d42-схем вариантов

Имя корневой d42-схемы строилось из операции и статуса, без content type. Два варианта
одного статуса с разными схемами затирали друг друга в модуле. Теперь базовое имя
остаётся у главного варианта слота (`application/json`, затем другие конкретные JSON,
затем `*/*` и `text/json`, затем текст, затем по алфавиту) и у вариантов с той же схемой, а к имени остальных добавляется content
type. Так появление `text/plain` рядом с JSON не переименовывает схему JSON-варианта.
У `*/*` суффикс `Any`. Если два content type дают один суффикс при разных схемах,
генерация падает с `NamespaceCollisionError`: числовой суффикс автоматически не
добавляется. При `d42: false` имена не проверяются.

# Waivers и `non_waivable`

Waiver — единственный способ пропустить конструкцию, которую нормализация иначе
отклонила бы. Он намеренно неудобен: послабление контракта должно быть заметным,
адресным и срочным, иначе через полгода это уже не послабление, а новый контракт.

## Формат

`waivers.yaml` лежит рядом с manifest (путь настраивается ключом `waivers`).

```yaml
version: 1
waivers:
  - operation: api.createDocument      # стабильный ключ операции
    direction: response                # request | response
    json_pointer: /body/payload        # contract path (см. ниже)
    rule: allow_any                    # что именно послабляется
    reason: "Бэкенд отдаёт свободную форму до перехода на v2"
    owner: "команда документов"
    issue: "TRACKER-1234"              # или ticket: <...>, но не оба сразу
    expires_at: 2026-12-31             # календарная дата, без времени
    expected_source: 9f2c...           # sha256 исходного фрагмента, 64 символа
    status: 200                        # необязательно: сузить до варианта ответа
    content_type: application/json     # необязательно: сузить до content type
```

Все поля кроме `status`, `content_type`, `replacement` и `values` обязательны. Неполный
waiver ломает генерацию.

### Contract path в `json_pointer`

Указывать исходный JSON Pointer документа
(`/components/schemas/Thing/properties/name`) было бы бессмысленно: стоит
вынести схему в `$ref` или обратно — и все waiver'ы протухнут, хотя контракт не
изменился. Поэтому адресация идёт по **форме данных**:

| Сегмент | Значение |
| --- | --- |
| `body` | корень тела запроса или ответа |
| `param/<in>/<name>` | параметр или заголовок |
| `<имя>` | свойство объекта |
| `-` | элементы массива |
| `+` | схема `additionalProperties` |
| `#0` | вариант `oneOf`/`anyOf` или часть `allOf` по индексу |

Экранирование — по RFC 6901 (`~0` для `~`, `~1` для `/`) плюс одно расширение:
свойство, чьё имя совпадает со служебным сегментом, пишется с префиксом `~2`
(`/~2-` — это свойство с именем `-`, а не элементы массива). Пустые сегменты
запрещены.

Примеры: `/body/rc`, `/body/groups/-/title`, `/param/query/filter`,
`/body/payload/#1/id`.

### Правила

| `rule` | Что послабляется |
| --- | --- |
| `allow_any` | неподдержанная конструкция заменяется узлом «что угодно» |
| `allow_unknown_format` | принимается `format`, которого нет в allowlist |
| `replace_schema` | фрагмент схемы заменяется явно заданным (`replacement` обязателен) |
| `relax_required` | поле становится необязательным вопреки спецификации |
| `ignore_read_only` | ошибочный `readOnly` не удаляет это поле из request |
| `ignore_write_only` | ошибочный `writeOnly` не удаляет это поле из response |
| `allow_null` | свойство дополнительно допускает `null` |
| `ignore_discriminator` | локальный `discriminator` не применяется |
| `extend_enum` | enum дополняется литералами из обязательного списка `values` |
| `add_property` | в объект добавляется необязательное свойство из `replacement` |
| `allow_unsupported_serialization` | принимается неподдержанное сочетание `style`/`explode` |

`replacement` допустим для `replace_schema` и `add_property` и обязателен для них.
`values` допустим и обязателен только для `extend_enum`. Несколько независимых
правил могут исправлять одну точку, например `ignore_read_only` вместе с
`allow_null`; `allow_any`, `replace_schema` и `add_property` остаются
эксклюзивными, потому что заменяют точку целиком.

## Как получить `expected_source`

Не вручную. Сообщение об ошибке генерации печатает **готовую заготовку** waiver'а
вместе с посчитанным отпечатком:

```
$ openapi-contracts update
ошибка: схема без type и без единого ограничения принимает что угодно.
Библиотека не подставляет 'любое значение' молча (contract path /body/payload)
Если это осознанное исключение, добавьте в waivers.yaml:
  - operation: api.createDocument
    direction: response
    json_pointer: /body/payload
    rule: allow_any
    expected_source: 4c1f8a...c93b
    reason: <зачем>
    owner: <кто отвечает>
    issue: <ссылка>
    expires_at: <YYYY-MM-DD>
 [source=openapi.yaml, operation=api.createDocument, direction=response,
  pointer=/paths/~1documents/post/responses/200/content/application~1json/schema/properties/payload]
```

Копируете, дописываете четыре поля про людей и срок — и всё.

Для дефектов, которые генерация сама обнаружить не может (`readOnly` на реально
принимаемом поле, неполный enum или отсутствующее свойство), отпечаток считается
той же функцией библиотеки, а не вручную:

```python
from openapi_contracts.waivers import waiver_source_digest

expected_source = waiver_source_digest(
    {"type": "string", "readOnly": True},
    "ignore_read_only",
)
```

Для `add_property` исходный фрагмент — отсутствие свойства, поэтому используется
`waiver_source_digest(None, "add_property")`. Когда свойство появится в OpenAPI,
waiver перестанет использоваться и сломает `update`/`check` до явного удаления.

## Жизненный цикл: что ломает генерацию

| Ситуация | Почему это ошибка |
| --- | --- |
| `expires_at` в прошлом | послабление просрочено; продлить надо осознанно |
| `expires_at` дальше `policies.waiver_max_days` (90 дней по умолчанию) | «навсегда» — это не срок |
| `expires_at` со временем (`2026-12-31T10:00:00Z`) | принимается только календарная дата: иначе отпечаток артефакта зависел бы от часового пояса |
| не заполнено обязательное поле | неполный waiver не принимается |
| два одинаковых waiver'а | избыточность |
| несовместимое правило замены вместе с другим правилом на одной точке | порядок применения был бы неопределённым |
| waiver ни разу не понадобился | контракт починился — послабление пора убрать |
| `expected_source` разошёлся с фактическим | исходный фрагмент изменили; послабление надо пересмотреть, а не продлевать вслепую |
| ссылка на несуществующую операцию | опечатка в ключе |
| пересечение с `non_waivable` | закреплённое свойство нельзя ослабить |

Проверка «waiver ни разу не понадобился» — самая полезная из них: без неё
`waivers.yaml` за год превращается в свалку, где непонятно, что ещё нужно.

## Изоляция: waiver не течёт в соседние операции

Это ключевое свойство. Если waiver адресует точку внутри схемы, на которую
ссылаются несколько операций, послабление получает **только** та операция, что
названа в waiver'е.

Механика: путь waiver'а вычисляется заранее, и любой `$ref`, стоящий на этом
пути, при нормализации разворачивается по месту вместо превращения в общее
именованное определение. Соседние операции продолжают ссылаться на строгую
версию схемы.

То же и с направлением: waiver на `response` не касается `request`, потому что
контракты направлений нормализуются независимо.

## Сужение до варианта

У операции может быть несколько ответов, и один и тот же contract path в них
означает разные фрагменты спецификации. Поля `status` и `content_type` сужают
область действия:

```yaml
  - operation: api.createDocument
    direction: response
    status: 400                    # только ошибочный ответ
    content_type: application/json
    json_pointer: /body/details
    rule: allow_any
    ...
```

Без сужения waiver применяется ко всем вариантам направления. Если фрагменты в
них разные, отпечаток не совпадёт и генерация упадёт с подсказкой сузить waiver.

## `non_waivable` — что нельзя ослабить никогда

Объявляется в manifest, у операции:

```yaml
operations:
  api.createDocument:
    source: main
    operation_id: createDocument
    non_waivable:
      - direction: response
        json_pointer: /body/rc
        rules: [required, non_null, non_empty_enum]
```

| Правило | Что закрепляет |
| --- | --- |
| `present` | поле существует в контракте (не удалено и не переименовано) |
| `required` | поле остаётся обязательным |
| `non_null` | поле не может стать nullable |
| `non_empty_enum` | у поля есть непустой `enum` |

Нарушение любого из них — ошибка генерации. Waiver, пересекающийся с
`non_waivable` по операции, направлению и пути, тоже ошибка: иначе защита
снималась бы тем же механизмом, от которого защищает.

Это инструмент для полей, на которых держится смысл тестов: код возврата,
статус сущности, признак успеха. Всё остальное пусть эволюционирует свободно.

## Политики

```yaml
policies:
  waiver_max_days: 90        # максимальный срок жизни waiver'а от сегодня
  unknown_formats: reject    # reject | annotate
```

`unknown_formats: annotate` принимает любые `format` без waiver'ов — разумно для
проектов, где генератор спецификации складывает в `format` собственные теги.
Формат при этом попадает в артефакт, но не участвует в валидации.

# Матрица поддержки OpenAPI 3.0.x и Swagger 2.0

Таблицы ниже описывают **фактическое** поведение версии 0.1 и выведены из
констант в коде: `normalization/schemas.py` (`_KNOWN_KEYWORDS`,
`_REJECTED_KEYWORDS`, `SUPPORTED_FORMATS`), `normalization/parameters.py`
(`SUPPORTED_SERIALIZATION`) и адаптеров в `dialects/`.

Главный принцип — **fail closed**. У конструкции есть ровно три состояния:

* **поддержано** — переносится в контракт точно;
* **аннотация** — распознаётся и осознанно отбрасывается, на контракт не влияет;
* **отклоняется** — генерация падает с точным JSON Pointer и объяснением.

Состояния «частично поддержано» и «интерпретируется приблизительно» отсутствуют
намеренно: молча ослабить контракт хуже, чем отказаться его строить.

## Версии документов

| Версия | Поведение |
| --- | --- |
| `swagger: "2.0"` | поддержано |
| `openapi: 3.0.x` | поддержано |
| `openapi: 3.1.x` | **отклоняется** с диагностикой, объясняющей несовместимость (см. ниже) |
| `swagger: "1.x"` | отклоняется |
| документ без `swagger` и `openapi` | отклоняется |

OpenAPI 3.1 — не надмножество 3.0: в нём удалён `nullable`,
`exclusiveMinimum`/`exclusiveMaximum` стали числовыми, `type` может быть
массивом, появились булевы схемы и `$defs`. Разбор 3.1 правилами 3.0 молча
потерял бы `null` в типах и неверно прочитал границы, поэтому библиотека
отказывается. Адаптер 3.1 добавляется отдельным модулем `dialects/openapi31.py`
без изменений в ядре.

### Про `oneOf` и d42

`oneOf` в проекции d42 становится `schema.any(...)`, то есть **шире** исходного
контракта: значение, подходящее сразу двум ветвям, d42 пропустит. Это
задокументированное расширение, а не потеря контракта: точная семантика остаётся
в JSON Schema, а валидация тела всегда идёт **двумя независимыми путями** —
d42 и JSON Schema. Отключить JSON-Schema-путь нельзя.

### Про невыразимые в d42 конструкции

Если конструкция точна в контракте и в JSON Schema, но не выразима в d42
(несливаемый `allOf`, `multipleOf`,
`minProperties`, рекурсия, `pattern` вместе с границами длины), библиотека
**не роняет операцию**. Она:

1. генерирует контракт и JSON Schema как обычно;
2. отключает d42 для этой операции и записывает причину в
   `contracts/<slug>.json` (`d42.enabled: false`, `d42.reason`);
3. печатает причину в выводе `openapi-contracts update`;
4. падает с этой же причиной при попытке получить d42-схему операции.

Ничего не пропадает молча — просто не работает та часть, которая физически не
может работать.

## `format`

Проверка `format` включена (`jsonschema` с `FormatChecker`). Известные значения:

| `type` | Допустимые `format` |
| --- | --- |
| `string` | `binary`, `byte`, `date`, `date-time`, `duration`, `email`, `hostname`, `idn-email`, `idn-hostname`, `ipv4`, `ipv6`, `iri`, `iri-reference`, `json-pointer`, `password`, `regex`, `relative-json-pointer`, `time`, `uri`, `uri-reference`, `uuid` |
| `integer` | `int32`, `int64` |
| `number` | `float`, `double` |
| `boolean`, `object`, `array` | ни одного |

Неизвестный `format` по умолчанию **отклоняется**. Два способа принять его
осознанно:

* `policies.unknown_formats: annotate` в manifest — для всего проекта;
* waiver с правилом `allow_unknown_format` — точечно.

`int32` и `int64` превращаются в явные знаковые границы, потому что JSON Schema
сама не считает их ограничениями диапазона. `format: binary` и `format: byte`
относятся к словарю OpenAPI, а не JSON Schema,
поэтому попадают в артефакт, но валидацию не выполняют.

## Параметры

| Расположение | Swagger 2.0 | OpenAPI 3.0 |
| --- | --- | --- |
| `path` | поддержано | поддержано |
| `query` | поддержано | поддержано |
| `header` | поддержано | поддержано |
| `cookie` | нет в спецификации | поддержано |
| `body` | поддержано (→ тело запроса) | заменён на `requestBody` |
| `formData` | **отклоняется**: у form-кодированного тела нет JSON-контракта | — |
| параметр через `content` | — | отклоняется |
| параметр через `$ref` | поддержано | поддержано |
| параметры уровня Path Item | поддержано, сливаются по паре `(name, in)` | поддержано |

### Сериализация

Поддержаны ровно эти сочетания; всё остальное отклоняется, потому что разбирать
значение приблизительно нельзя.

| `in` | `style` | `explode` | Форма значения |
| --- | --- | --- | --- |
| `path` | `simple` | `false` | скаляр; массив через запятую |
| `query` | `form` | `true` | скаляр; массив как повторяющийся ключ |
| `query` | `form` | `false` | скаляр; массив через запятую |
| `query` | `spaceDelimited` | `false` | массив через пробел |
| `query` | `pipeDelimited` | `false` | массив через `|` |
| `header` | `simple` | `false` | скаляр; массив через запятую |
| `cookie` | `form` | `true` / `false` | скаляр |

Отклоняются: `deepObject`, `label`, `matrix`, `allowReserved`, объекты в
параметрах, вложенные массивы и массивы объектов.

`collectionFormat` Swagger 2.0 отображается так: `csv` → `form`/`explode=false`,
`multi` → `form`/`explode=true`, `ssv` → `spaceDelimited`, `pipes` →
`pipeDelimited`; `tsv` отклоняется.

## Тела и ответы

| Конструкция | Поведение |
| --- | --- |
| `requestBody.content` (3.0) / `in: body` + `consumes` (2.0) | поддержано |
| несколько request content type | поддержано; в manifest можно закрепить один через `request.content_type` |
| `responses.<код>` | поддержано |
| `responses.default` | поддержано; при моке требуется явный числовой `status` |
| диапазоны кодов (`2XX`) | отклоняются |
| ответ без тела (204 и пустой `default`) | поддержано, `schema: null` |
| несколько media type в одном ответе | поддержано |
| `application/json` и `<...>+json` | поддержано |
| `application/json;charset=UTF-8` | поддержано: параметры отбрасываются, регистр нормализуется |
| `*/*` в Swagger 2.0 | считается JSON-совместимым (так его генерируют серверные фреймворки) |
| не-JSON media type (`application/pdf`, `text/plain`, …) | вариант **записывается** в артефакт с причиной, контракт тела не строится |
| заголовки ответа | поддержаны, включая `$ref` и пустой `headers: {}` |

## `$ref`

| Вид ссылки | Поведение |
| --- | --- |
| локальная в том же файле | поддержано |
| межфайловая внутри `sources.<name>.root` | поддержано |
| межфайловая за пределами `root` | **отклоняется** |
| через symlink, ведущий за `root` | **отклоняется** (путь проверяется после `resolve()`) |
| `http(s)://` | **отклоняется всегда**: библиотека не ходит в сеть |
| `$ref` рядом с `description`/`title`/`example`/`summary` | принимается, соседи отбрасываются |
| `$ref` рядом с `readOnly`/`writeOnly`/`nullable` | принимается, соседи **применяются** |
| `$ref` рядом с любым другим ключом | **отклоняется**: OpenAPI 3.0 молча его игнорирует, а терять контракт молча нельзя |
| глубокие цепочки ссылок | поддержаны, ограничения на глубину нет |
| рекурсия (прямая и взаимная) | контракт и JSON Schema строятся; d42 отключается с причиной |

## Прочее

| Конструкция | Поведение |
| --- | --- |
| `basePath` (2.0) | входит в маршрут; можно перекрыть через `sources.<name>.base_path` |
| `servers` (3.0) | в маршрут не подмешивается — это адрес развёртывания; префикс задаётся `base_path` |
| `info` без `title`/`version` | принимается: реальные генераторы так делают |
| `operationId` отсутствует | в режиме `all` — ошибка; в `explicit` операция ищется по `method` + `path` |
| `operationId` дублируется | ошибка с указанием обоих маршрутов |
| переменная маршрута — невалидный Python-идентификатор | поддержано: имена path-параметров не преобразуются |
| несовпадение шаблона маршрута и объявленных path-параметров | **отклоняется** |
| `security`, `securitySchemes`, `callbacks`, `links`, `webhooks` | не читаются: на контракт данных не влияют |
| YAML и JSON | оба поддержаны, загрузка только через `yaml.safe_load` |
